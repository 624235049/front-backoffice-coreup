# 10 — Consult + ระบบ: ช่วยองค์กรเล็กที่ไม่เคยมีระบบได้อย่างไร

ไฟล์นี้อธิบายว่า **งานที่ปรึกษากับตัวระบบทำงานด้วยกันอย่างไร** และผลต่อการออกแบบระบบ ทั้งทีมที่ปรึกษาและ dev ควรอ่าน

---

## 1. ความจริงของร้านที่ไม่เคยมีระบบ

"ระบบ" ของร้านเหล่านี้ตอนนี้คือ:

- **หัวเจ้าของ** — ทุกการตัดสินใจต้องผ่านเจ้าของ
- **แชต LINE** — นัด สั่งงาน ตามงาน ทะเลาะ อยู่ในกลุ่มเดียวกัน
- **สมุด / กระดาน / Excel** — ของใครของมัน ไม่ตรงกัน
- **ความจำของคนเก่า** — คนเก่าออก ความรู้ออกตาม

ปัญหาจริงไม่ใช่ "ไม่มีโปรแกรม" แต่คือ **ไม่มีใครเคยเขียนวิธีทำงานลงมาให้ชัด** การติดตั้งโปรแกรมให้อย่างเดียวจึงล้มเหลว

## 2. ทำไมต้องขายคู่กัน

| ขายอย่างเดียว | ผล |
|---|---|
| ที่ปรึกษาอย่างเดียว | ร้านดีขึ้นช่วงที่เราอยู่ พอเราออก ทุกอย่างกลับไปเหมือนเดิมใน 2–3 เดือน |
| ระบบอย่างเดียว | ไม่มีใครตั้งค่า ไม่มีใครพาทีมใช้ เลิกใช้ภายในเดือนแรก |
| **ที่ปรึกษา + ระบบ** | ที่ปรึกษาเปลี่ยนวิธีทำงาน → ระบบ **ล็อกวิธีใหม่ไว้** ให้อยู่ต่อหลังเราออก และ **พิสูจน์ผลด้วยตัวเลข** |

ประโยคขาย: **"เราไม่ได้ขายโปรแกรม เราวางระบบให้ร้าน แล้วทิ้งระบบไว้ให้ร้านเดินต่อได้เอง"**

ระบบจึงไม่ใช่สินค้าแยก แต่เป็น **เครื่องมือของที่ปรึกษา** ที่ร้านใช้ต่อหลังจบงาน → ค่าระบบรายเดือนคือรายได้ประจำหลังงานที่ปรึกษาจบ

## 3. หลัก 7 ข้อในการพาร้านเข้าระบบ

1. **เริ่มจากสิ่งที่ร้านทำอยู่แล้ว** — เอาสมุดนัดเข้าระบบก่อน ยังไม่เปลี่ยนวิธีทำงาน ห้ามเปลี่ยน "เครื่องมือ" กับ "วิธีทำงาน" พร้อมกัน
2. **ชนะเร็วภายใน 14 วัน** — เรื่องแรกต้องเห็นผลเร็วและทุกคนชอบ: LINE เตือนนัด (หน้าร้านทำงานน้อยลงทันที ลูกค้ามาตรงเวลาขึ้น)
3. **พนักงานต้องได้ประโยชน์ก่อนเจ้าของ** — ร้านที่ toxic จะต้านระบบที่ดูเหมือน "สายลับเจ้าของ" ให้พนักงานเห็นรายได้ตัวเองทุกวัน เห็นเหตุผลการแบ่งคิว ไม่ต้องจำงาน → พนักงานเป็นคนอยากใช้
4. **วัดก่อนเปลี่ยน** — 2 สัปดาห์แรกระบบเก็บตัวเลขฐาน (baseline) ก่อนแก้อะไร ไม่งั้นพิสูจน์ผลไม่ได้
5. **เรื่องเงินและคิวทำทีหลัง และทำผ่านการคุย** — กติกาค่ามือ/คิวแตะผลประโยชน์ ต้องให้ที่ปรึกษาพาคุยจนทีมยอมรับ แล้วค่อยใส่ในระบบ ห้ามตั้งในระบบแล้วประกาศ
6. **มีคนในร้านเป็นเจ้าของระบบ** — แต่งตั้ง "ผู้ดูแลระบบในร้าน" 1 คน ฝึกให้ตั้งค่าเองได้ ก่อนเราออก
7. **ย้ายการตัดสินใจจากหัวเจ้าของ ไปเป็นกติกา** — ทุกครั้งที่เจ้าของต้องตัดสินเรื่องซ้ำ ๆ (ใครได้คิว ลาได้ไหม ลดราคาได้ไหม) แปลงเป็นกติกาในระบบหรือมอบอำนาจให้หัวหน้า

## 4. แผน 90 วันมาตรฐาน (CoreUp Playbook)

| ช่วง | ที่ปรึกษาทำ | ระบบที่เปิด | ร้านได้อะไร |
|---|---|---|---|
| **สัปดาห์ 0** | คุยเจ้าของ ตกลงกติกา (ความลับ เป็นกลาง เจ้าของรับฟังผล) · โปรไฟล์ร้าน | สร้างร้านจาก template · เชื่อม LINE OA | — |
| **สัปดาห์ 1–2** | ย้ายนัดจากสมุด/แชตเข้าระบบ · ฝึกหน้าร้าน 30 นาที | **นัด + LINE เตือน** · เก็บ baseline | หน้าร้านไม่ต้องไล่โทร (ชนะเร็ว) |
| **สัปดาห์ 2–4** | ออดิท: แบบสอบถาม สัมภาษณ์ ดูหน้างาน · ให้คะแนน 7 ด้าน | **แบบสอบถาม + แจ้งปัญหา** | เจ้าของเห็นภาพร้านจริงเป็นครั้งแรก |
| **สัปดาห์ 4** | รายงานผลกับเจ้าของ (ตัวต่อตัว) → เลือก 2–3 เรื่อง · สรุปให้ทีมฟัง | รายงานออดิท | แผน 90 วัน |
| **สัปดาห์ 5–8** | เขียนหน้าที่ต่อกะ เช็กลิสต์ คู่มือ **ร่วมกับทีม** · เลือกหัวหน้าคนกลาง | **กะ + เช็กลิสต์ + คู่มือ + ติดตามหลังทำ** | เจ้าของหยุดโทรเช็กร้าน |
| **สัปดาห์ 8–10** | พาคุยกติกาคิว/ค่ามือจนตกลงได้ · ทดลองกับตัวจำลองต่อหน้าทีม | **คิว + ค่ามือ + ปิดวัน** | เลิกทะเลาะเรื่องคิวและเงิน |
| **สัปดาห์ 10–12** | ฝึกผู้ดูแลระบบในร้าน · ออดิทซ้ำ · เทียบก่อน–หลัง | **รายงาน + KPI** · อนุมัติผ่านหัวหน้า | ร้านเดินเองได้ + ตัวเลขพิสูจน์ผล |
| **หลัง 90 วัน** | ติดตามเดือนละครั้ง (ถ้าซื้อ) | ระบบรายเดือนต่อ | ระบบอยู่ต่อ |

### เลือก "ชนะเร็ว" ให้ตรงกับร้าน (ไม่ใช่ LINE เตือนนัดเสมอ)

ระบบนัด + เตือนผ่าน LINE **มีคนทำแล้วหลายเจ้า** โดยเฉพาะโปรแกรมคลินิกและระบบจัดการแชต LINE OA จึงไม่ใช่จุดขายหลักของเรา เป็นแค่ประตูเข้าร้านที่ยังไม่มีระบบ

| ร้านมีอะไรอยู่แล้ว | ชนะเร็วที่ใช้ | ระบบนัดของเรา |
|---|---|---|
| ยังไม่มีระบบนัด (สปา ร้านนวด ร้านสระผม คลินิกเล็กส่วนใหญ่) | นัด + LINE เตือน | เปิดใช้ |
| มีโปรแกรมคลินิก/ระบบจองที่เตือน LINE แล้ว | **การ์ดหน้าที่ต่อกะ + เช็กลิสต์ + สรุปปิดวันเข้า LINE เจ้าของ** หรือ **รายได้ของฉัน** ให้พนักงานเห็นทุกวัน | ไม่เปิด — import ยอด/นัดรายวันจากระบบเดิมแทน ห้ามให้กรอกซ้ำ |

### จุดยืนเทียบกับระบบที่มีอยู่ในตลาด

- โปรแกรมคลินิก / ระบบจอง / ระบบแชต LINE = **เครื่องมือจัดการลูกค้า**
- CoreUp = **ที่ปรึกษา + ระบบจัดการคนและการทำงานภายในร้าน** (หน้าที่ต่อกะ ความยุติธรรมเรื่องคิวและเงิน เสียงพนักงาน ลดการพึ่งเจ้าของ) ทำงาน **ร่วมกับ** ระบบเดิมของร้านได้
- ห้ามขายแข่งเรื่อง "เตือนนัดได้" อย่างเดียว ต้องขายเรื่อง "ร้านเดินได้เองและคนไม่ลาออก"

### ทางลัดสำหรับร้านเล็กมาก (≤ 5 คน)

"**ตั้งระบบร้านเล็ก**" 2–4 สัปดาห์: ใช้ template ตามธุรกิจ + ที่ปรึกษาออนไลน์ 3 ครั้ง (ตั้งค่า, ฝึก, ทบทวน) ไม่ต้องออดิทเต็ม ราคาต่ำ ขายได้จำนวนมาก แล้วค่อยเสนอออดิทเมื่อร้านโต

## 5. ตัวเลขที่บอกว่าเราช่วยได้จริง

### 5.1 ของร้าน (โชว์ในรายงานก่อน–หลัง)

| ตัวเลข | ทำไมสำคัญ |
|---|---|
| **เรื่องที่ต้องผ่านเจ้าของต่อวัน** (Owner dependency) | ตัวชี้วัดหลักว่า "ร้านเดินเองได้" — นับจาก อนุมัติ ลา แลกเวร ส่วนลด การ override คิว ที่เจ้าของต้องทำเอง |
| ชั่วโมงงานธุรการต่อวัน | ประเมินจากจำนวนข้อความ/การโทรที่ระบบทำแทน |
| No-show, ยืนยันนัด | ผลเร็วที่สุด |
| ลูกค้ากลับมาใน 90 วัน | ผลต่อรายได้ |
| ลาออก / คนใหม่อยู่ไม่ถึง 90 วัน | ผลด้านคน |
| คะแนนความยุติธรรม, eNPS | ผลด้านบรรยากาศ |

### 5.2 ของ CoreUp (ใช้วัดว่าวิธีของเราได้ผลไหม)

| ตัวเลข | เป้า |
|---|---|
| เวลาถึงผลแรก (วันที่ส่ง LINE เตือนนัดครั้งแรก) | ≤ 7 วันหลังเซ็น |
| พนักงานที่ใช้ระบบทุกสัปดาห์ | ≥ 80% ของพนักงานร้าน |
| ร้านที่จบ 90 วันแล้วใช้ระบบต่อ | ≥ 70% |
| ร้านที่ owner dependency ลดลง ≥ 30% | ≥ 7 ใน 10 |

## 6. ผลต่อการออกแบบระบบ (สิ่งที่ dev ต้องทำเพิ่ม)

| ความต้องการจาก playbook | ฟีเจอร์ | Milestone |
|---|---|---|
| เปิดระบบเป็นขั้น ตามแผน 90 วัน | ที่ปรึกษาเปิด/ปิดโมดูลต่อร้านได้เอง + `uiMode` | M2 |
| ย้ายข้อมูลจากสมุด/Excel เร็ว | Import CSV + **กรอกนัดล่วงหน้าแบบเร็ว** (พิมพ์รัว ๆ หลายนัดในหน้าเดียว) | M2 |
| Baseline ก่อนเปลี่ยน | ทุก KPI มีจุด "เริ่มใช้งาน" + ช่วง baseline 14 วันแรก ใช้เป็นจุดเทียบอัตโนมัติ | M7 (เก็บข้อมูลตั้งแต่ M2) |
| วัด owner dependency | นับทุก action ที่ทำโดย role owner ประเภทอนุมัติ/override/ตอบคำถาม → KPI `owner_dependency` | M6 |
| ผู้ดูแลระบบในร้าน | permission set "tenant_champion" ตั้งค่าเช็กลิสต์ คู่มือ ข้อความ ได้ แต่ไม่เห็นเงิน | M4 |
| ที่ปรึกษาติดตามหลายร้านพร้อมกัน | `/platform` แสดงความคืบหน้าแผน 90 วันต่อร้าน + การใช้งาน + สัญญาณเสี่ยง | M5 |
| ตัวจำลองกติกาต่อหน้าทีม | `/rules/*` simulate ใช้ข้อมูลจริงของร้านย้อนหลัง 30 วัน: "ถ้าใช้กติกานี้ เดือนที่แล้วแต่ละคนจะได้เท่าไร" | M6 |
| Playbook เป็นข้อมูล | `playbooks` + `engagement_tasks` (งานรายสัปดาห์ของที่ปรึกษา พร้อม checklist) ใน backoffice | M5 |
| ไม่ทำฟีเจอร์เฉพาะร้าน | ทุกคำขอพิเศษต้องตอบด้วย template / rule / custom field ก่อน ถ้าทำไม่ได้ → เก็บเป็นคำขอ รอ ≥ 3 ร้านขอเหมือนกันจึงทำ | ตลอด |

ตารางเพิ่ม:

`playbooks` `id, key, name, version, weeks jsonb ([{week, title, tasks:[{key, title, owner:'consultant'|'tenant', moduleToEnable?}]}])`
`engagement_tasks` `id, engagement_id, week, key, title, owner, status, due_on, done_at, note`
`feature_requests` `id, tenant_id, title, body, requested_by, category, votes int, status`

## 7. แผนที่ "ปัญหา → ต้นเหตุ → ทางแก้" (ให้แก้ตรงจุด ไม่ใช่แก้อาการ)

กติกา: **ห้ามเปิดฟีเจอร์ให้ร้านโดยไม่มีปัญหาในตารางนี้รองรับ** และทุกแถวต้องมีตัวเลขที่บอกว่าแก้ได้จริง ถ้าตัวเลขไม่ขยับใน 30 วัน แปลว่าแก้ผิดจุด ต้องกลับไปดูต้นเหตุใหม่

| อาการที่เจ้าของเห็น | ต้นเหตุที่มักเจอจริง | ที่ปรึกษาทำ | ระบบทำ | ตัวเลขพิสูจน์ |
|---|---|---|---|---|
| ลูกค้านัดแล้วไม่มา | ไม่มีใครเตือน / เตือนไม่สม่ำเสมอ / ลูกค้าเลื่อนยากต้องโทร | กำหนดจังหวะเตือนกับร้าน | LINE ยืนยัน + เตือน + ปุ่มเลื่อนเอง | no-show, อัตรายืนยัน |
| ลูกค้าไม่กลับมา | ไม่มีใครติดตาม / ไม่รู้ว่าถึงรอบ / ลูกค้าผูกกับพนักงานที่ลาออก | กำหนดคนดูแลลูกค้า + สคริปต์ติดตาม | งานติดตามอัตโนมัติ + เตือนรอบ + ลูกค้ามี "เจ้าของร้าน" ไม่ใช่ของพนักงานคนเดียว | กลับมาใน 90 วัน, ลูกค้าหายตามพนักงาน |
| พนักงานทะเลาะ / แบ่งก๊ก | แบ่งคิวและลูกค้าไม่ชัด / ค่ามือไม่โปร่งใส / คนสนิทได้เปรียบ | พาคุยตั้งกติกาที่ทุกคนยอมรับ | คิวตามกติกาพร้อมเหตุผล + ค่ามือเห็นที่มา + override ต้องมีเหตุผล | คะแนนความยุติธรรม, จำนวน override |
| คนลาออกบ่อย | ไม่รู้หน้าที่ / ไม่มีคนสอน / ไม่มีทางเติบโต / หัวหน้าไม่เท่าเทียม | ผังงาน บันไดตำแหน่ง ฝึกหัวหน้า | การ์ดหน้าที่ + คู่มือ + แบบสอบถามรายเดือน + ช่องแจ้งปัญหา | ลาออก, ลาออกใน 90 วัน, eNPS |
| เจ้าของต้องอยู่ร้านตลอด | การตัดสินใจทั้งหมดอยู่ที่เจ้าของ / ไม่มีหัวหน้า / ไม่มีข้อมูลให้ดูจากที่อื่น | ย้ายเรื่องซ้ำ ๆ เป็นกติกา + มอบอำนาจหัวหน้า | กล่องอนุมัติของหัวหน้า + เช็กลิสต์ + สรุปปิดวันเข้า LINE | owner dependency |
| บริการไม่เหมือนกันแต่ละคน | ไม่มีมาตรฐานเขียนไว้ / คนใหม่เรียนจากการดู | เขียน SOP กับคนที่ทำดีที่สุด | SOP ผูกกับบริการ + ยืนยันการอ่าน | คะแนนลูกค้าต่อพนักงาน, รีวิว |
| คนหนึ่งลา ร้านพัง | งานผูกกับตัวคน / ไม่มีคนทำแทน | สอนข้ามตำแหน่ง (ทุกงานมี 2 คนทำได้) | ทักษะต่อคน + เสนอคนแทนอัตโนมัติ | นัดที่ต้องยกเลิกเพราะพนักงานลา |
| ยอดขึ้นแต่กำไรไม่ขึ้น | ส่วนลดไม่มีการควบคุม / ค่ามือไม่สัมพันธ์กับราคา / เวลาว่างเยอะ | ทบทวนโครงสร้างค่ามือและราคา | ส่วนลดต้องมีเหตุผล + รายงานการใช้ห้อง/เวลา | ส่วนลด/ยอด, การใช้ห้อง |
| เจ้าของไม่รู้ว่าเกิดอะไรในร้าน | พนักงานไม่กล้าพูด / ข้อมูลอยู่ในแชต | สร้างความไว้ใจ (ความลับ, เป็นกลาง) | แบบสอบถามไม่ระบุตัว + แจ้งปัญหา + รายงาน | จำนวนเรื่องที่แจ้งและปิดได้ |

> ถ้าออดิทแล้วพบว่าต้นเหตุคือ **วิธีบริหารของเจ้าของเอง** ระบบช่วยได้น้อย ต้องเป็นงานที่ปรึกษาคุยกับเจ้าของโดยตรง — ห้ามขายระบบเพิ่มเพื่อแก้ปัญหานี้

## 8. ความเสี่ยงของโมเดลนี้ และวิธีกัน

| ความเสี่ยง | วิธีกัน |
|---|---|
| กลายเป็นฝ่ายซัพพอร์ตโปรแกรม ไม่มีเวลาทำงานที่ปรึกษา | ผู้ดูแลระบบในร้านรับเรื่องแรก · คู่มือในระบบ · ซัพพอร์ตตามช่องทางและเวลาที่กำหนด |
| ทุกร้านขอแก้ระบบให้ตรงกับตัวเอง (dev คนเดียวรับไม่ไหว) | กฎ "3 ร้านขอเหมือนกันจึงทำ" + ทุกอย่างผ่าน template/rule/custom field |
| เจ้าของไม่ยอมรับผลออดิท | ตกลงกติกาตั้งแต่สัปดาห์ 0 · เล่าผลด้วยตัวเลขและเสียงพนักงาน ไม่ใช่ความเห็นที่ปรึกษา |
| พนักงานไม่ไว้ใจ | ไม่ระบุตัวตนจริงในระบบ · ร้านเห็นประวัติการเข้าดูของ CoreUp · พนักงานได้ประโยชน์ก่อน |
| ขยายบริษัทไม่ได้เพราะทุกอย่างอยู่ในหัวผู้ก่อตั้ง | Playbook + template + rubric อยู่ในระบบ → ฝึกที่ปรึกษาใหม่ได้ |
| ร้านเลิกจ่ายค่าระบบหลังจบงาน | ระบบต้องผูกกับงานประจำวัน (นัด คิว ค่ามือ) ไม่ใช่แค่รายงาน · รายงานเดือนส่งให้เจ้าของเห็นคุณค่าทุกเดือน |
