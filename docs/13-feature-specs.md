# 13 — Spec ฟังก์ชัน: ใช้แล้วต้องเห็นว่าช่วยได้จริง

หลักข้อเดียวของไฟล์นี้: **ทุกฟังก์ชันต้องบอกผู้ใช้ได้ว่า "ช่วยอะไรไปแล้ว" ทันทีบนหน้าจอ** ถ้าระบบทำงานแทนคนแต่ไม่มีใครเห็น ร้านจะรู้สึกว่าจ่ายเงินไปเปล่า ๆ

แต่ละฟังก์ชันเขียนในรูปแบบเดียวกัน:
**ใคร / ปัญหา → หน้าจอ (wireframe) → ระบบทำเองอะไร → สิ่งที่ผู้ใช้เห็นว่าช่วยได้ → API → ข้อมูล → เสร็จเมื่อ**

---

## 0. กลไกกลาง: "ระบบช่วยอะไรไปแล้ว" (Impact)

ทุกครั้งที่ระบบทำงานแทนคน → บันทึก `impact_events` (ดู 12-database-ddl.sql §7) พร้อมนาทีที่ประหยัดโดยประมาณ

| kind | เกิดเมื่อ | นาทีประหยัด (ค่าเริ่ม ร้านแก้ได้) |
|---|---|---|
| `reminder_sent` | ส่ง LINE เตือนนัดแทนการโทร | 1.5 |
| `confirm_by_customer` | ลูกค้ากดยืนยันเอง | 1.0 |
| `reschedule_self_service` | ลูกค้าขอเลื่อนผ่าน LINE | 3.0 |
| `followup_auto_created` | ระบบสร้างงานติดตามเอง | 2.0 |
| `no_show_recovered` | ลูกค้าที่ไม่มา ถูกนัดใหม่ได้ | 0 (นับเป็นเงินแทน) |
| `overlap_prevented` | กันนัดชน | 5.0 |
| `queue_auto_assigned` | จ่ายคิวตามกติกา | 1.0 |
| `payout_auto_calculated` | คิดค่ามือ 1 รายการ | 0.5 |
| `checklist_completed` | เช็กลิสต์ครบโดยไม่ต้องโทรถาม | 3.0 |
| `owner_decision_delegated` | หัวหน้าอนุมัติแทนเจ้าของ | 5.0 |
| `report_auto_sent` | สรุปส่งเข้า LINE แทนการทำรายงาน | 15.0 |

**แสดงที่ไหน**
- แถบบนสุดของ `/today`: "วันนี้ระบบส่งเตือน 28 · ลูกค้ายืนยันเอง 21 · กันนัดชน 1 · ประหยัด ~1 ชม. 10 นาที"
- การ์ดแรกของหน้าเจ้าของ: "เดือนนี้ระบบทำงานแทนทีม **31 ชั่วโมง** · ลูกค้ากลับมาจากการติดตาม **18 คน** ≈ **[ยอด] บาท**"
- รายงานเดือน (LINE): บรรทัดแรกเสมอ
- Backoffice CoreUp: รวมต่อร้าน → ใช้ตอนต่อสัญญา

API: `GET /v1/impact/summary?period=today|week|month&branchId=` → `{ totalMinutes, items:[{kind, count, minutes}], money:{recoveredMinor} }`

**ระบบทำเอง:** ดึงเฉพาะคนที่อยู่กะ · แสดงลา/พัก · สีตามสถานะยืนยัน · ย้ายนัดของคนลาไปคนที่ว่างและมีทักษะ (เสนอ แล้วหน้าร้านกดยืนยัน) · อัปเดตสดผ่าน SSE

**API:** `GET /v1/calendar?view=day&by=member&branchId=&date=` · `GET /v1/today-board?branchId=` (รวม: needsCheck, waitlist, nextInQueue, followupsDue, impactToday) · `GET /v1/stream/branch/:id` (SSE)

**เสร็จเมื่อ:** หน้าร้านลงนัด/เช็กอิน/จบงานได้ภายใน 3 แตะ · โหลด < 1.5 วินาทีบน iPad · ไม่ต้องรีเฟรชเอง

## 5. ความเสี่ยงคนสำคัญ `/team/risk` (เจ้าของ · ที่ปรึกษา)

**ปัญหา:** "ร้านไม่มีปัญหา" จนคนเก่งลาออก → ต้องทำให้ความเสี่ยงมองเห็นก่อนเกิด

```
ความเสี่ยงคนสำคัญ · สาขาสยาม                       คะแนนความต่อเนื่อง 58/100
──────────────────────────────────────────────────────────────────
ลูกค้าประจำผูกกับใคร          งานที่มีคนทำได้คนเดียว (6)
 แพร   ████████████ 32%          • นวดหินร้อน → แพรคนเดียว   [มอบหมายสอน]
 แอน   ███████ 18%               • ปิดยอดลิ้นชัก → นิด        [มอบหมายสอน]
 อื่น ๆ ████████████████ 50%      ...
 ⚠ ลูกค้า 41% ไม่มีผู้ดูแลสำรอง   [ตั้งผู้ดูแลสำรองอัตโนมัติ]
ความรู้ที่ยังไม่มีคู่มือ: 9 บริการ จาก 14   [ขอให้คนเก่าเขียน + ให้เครดิต]
──────────────────────────────────────────────────────────────────
ถ้าแพรลาออกพรุ่งนี้: ลูกค้าประจำเสี่ยง 46 คน ≈ ฿ [ยอดเฉลี่ย×ความถี่]/เดือน
```

**คำนวณ (domain `risk.ts`)**
- `customerConcentration`: % ลูกค้าประจำ (มา ≥ 3 ครั้งใน 180 วัน) ที่ ≥ 70% ของการมาเป็นกับพนักงานคนเดียว แยกต่อคน
- `singlePointTasks`: บริการที่มี `member_skills.level in ('can_do','can_teach')` แค่ 1 คน + เช็กลิสต์/หน้าที่ที่มีคนทำในรอบ 30 วันแค่ 1 คน
- `undocumented`: บริการ active ที่ไม่มี `services.sop_id`
- `continuityScore` = 100 − (น้ำหนักรวม 3 ตัวบน) — สูตรอยู่ใน domain + test
- `whatIfLeaves(memberId)`: ลูกค้าเสี่ยง + รายได้ต่อเดือนโดยประมาณ

**ระบบทำเอง:** เสนอผู้ดูแลสำรองให้ลูกค้าประจำ (กดยืนยันทีเดียว) · สร้างงาน "สอนงาน" ใน shifts · เตือนเมื่อคะแนนลดลง

**ฝั่งคนเก่า:** การสอนงานและเขียนคู่มือ → `commission_ledger.component = 'mentor_bonus' | 'sop_bonus'` (ถ้าร้านเปิดในกติกา) และแสดงใน "รายได้ของฉัน"

**API:** `GET /v1/risk/summary?branchId=` · `GET /v1/risk/what-if?memberId=` · `POST /v1/risk/assign-secondary` · `GET/PUT /v1/members/:id/skills`

**ข้อห้าม:** ไม่แสดงหน้านี้ให้พนักงานทั่วไป · ไม่ใช้คำว่า "ผูกขาด" ใช้ "ลูกค้าที่ดูแลหลัก"

## 8. คิวและกติกาที่โปร่งใส `/queue` + `/rules/queue`

- ทุกการจ่ายคิวแสดง **เหตุผลเป็นประโยค**: "แอน — ตามลำดับเวียน (คนก่อนหน้า: แพร รับลูกค้าที่ขอเอง ไม่นับรอบ)"
- override ได้ แต่ต้องเลือกเหตุผล → นับใน KPI `queue_override_rate` (ตัวชี้วัดความยุติธรรม)
- หน้าตั้งกติกามี **ตัวจำลองด้วยข้อมูลจริง 30 วัน**: "ถ้าใช้กติกานี้ เดือนที่แล้ว แพรได้ 42 คิว (+3) แอน 39 (−1)..." ใช้ตอนที่ปรึกษาพาทีมคุย

**API:** `GET /v1/queue/next` · `POST /v1/queue/assign` · `POST /v1/rules/queue/simulate { body, from, to }`

## 12. เครื่องคิดเงินรั่ว (landing page, ไม่ต้องล็อกอิน)

ช่องกรอก: นัดต่อวัน · % ไม่มา (ไม่รู้ → ใช้ค่ากลางที่ระบุว่าเป็นค่าประมาณ) · ยอดเฉลี่ยต่อบิล · พนักงานลาออกต่อปี · ค่าหาและสอนคนใหม่ต่อคน · % ลูกค้าที่ไม่กลับมา

ผล: "เดือนละประมาณ ฿X ที่อาจรั่ว" แยก 3 ก้อน + ปุ่ม "ขอตรวจร้านฟรีเพื่อดูตัวเลขจริง" → สร้าง lead พร้อม `leads.leak_estimate`

สูตรอยู่ใน `packages/domain/leak.ts` ใช้ร่วมหน้าเว็บและ backoffice (ทีมขายกรอกให้ร้านตอนคุย) — แสดงหมายเหตุเสมอว่าเป็นการประมาณจากข้อมูลที่กรอก

**API:** `POST /v1/public/leak-estimate` (คำนวณ + เก็บแบบไม่ระบุตัวจนกว่าจะกรอกฟอร์ม)
